# v0.1 UI Wrapper Plan

## Decision

Keep the first prototype simple:

- no message editing
- no message id cache
- no persistent state
- no task card lifecycle
- no progress bar

The goal is only to make the existing status update message feel more polished.

## UX

Each status update remains a standalone message, but is rendered as a small status card when supported.

Preferred Discord/semantic presentation:

- title: `OpenClaw 正在處理`
- body: concise Traditional Chinese status
- context: `OpenClaw status update`
- info tone / accent color

Text fallback:

```md
🦾 **OpenClaw 正在處理**
> 狀態更新：目前在檢查設定；下一步會驗證結果。
```

## Why this first

This removes the hardest B-mode risks:

- no message id storage
- no restart recovery problem
- no edit permission problem
- no concurrent task overwrite problem
- much less rate-limit pressure than edit loops

Remaining risks are the same as the current plugin:

- send failure
- route resolution failure
- channel capability differences

## Prototype tool

The lab registers `status_update_ui` instead of replacing `status_update`.

Reason:

- can test alongside the original plugin
- does not interfere with customer installs
- can later become an optional replacement or configurable mode after validation
